## 数据与随机生成

法杖持久数据至少包括 schema_version、实例标识、生成器版本、随机种子、阶级、类型、完整属性、固有效果、按序法术实例列表、剩余法力、牌库与弃牌堆中的卡片实例顺序、洗牌随机状态、回充累计修正和剩余冷却。当前手牌只存在于原子预载事务内，不单独跨存档恢复。保存最终生成结果，不能只保存种子后依赖未来算法重新生成。

法术定义包含 id、category、mana_cost、cast_delay_delta、recharge_delta、damage、speed、lifetime、child_count 和允许组合标签；卡片实例与定义分离。随机数使用独立序列，不干扰世界随机流。权威随机只在服务端运行。

生成流程：来源确定阶级 → 抽取类型 → 分配属性预算 → 决定乱序与固有卡 → 装配合法初始卡组 → 校验上下限 → 保存实体数据。定义阶级预算表与属性代价曲线，再用批量样本检查分布；避免“每项独立抽区间”产生极端全优法杖。异常生成回退到同阶安全模板。

## 三段式外观与初始化

外观数据增加 appearance_schema、head_id、body_id、tail_id、storage_detail_id 与 appearance_revision。保存最终部件选择，不在客户端重新随机，也不因素材清单顺序变化而改变旧物品外观。部件使用稳定 ID，并在删除资源时提供兼容映射。

生成流程补充为：先确定完整属性 → 按乱序和基础抽取数筛选杖头 → 按容量筛选杖身长度 → 按回复档筛选杖尾 → 在合法部件池内随机选择样式 → 添加法力上限装饰 → 保存属性及外观描述。六类法杖只影响生成权重，不限定部件只能同套搭配。属性升级若未来加入，应同时重新计算受影响的视觉标记，保留仍然合法的样式选择。

所有部件遵守统一轴向、连接宽度、透明留边、层级与连接点规范。以握持点为坐标原点，长短由分档绘制的杖身和相应端点位置实现；不拉伸整根贴图导致水晶和杖尾变形。杖头外向尖端与中央水晶需要独立识别，双尖带水晶不能视觉上变成三尖。

首选改为“独立部件素材 + 多 symbol 动画模板 + 运行时替换”。模板包含 head、body、tail 与可选储能装饰，各 symbol 有明确层级与连接点。地面物品自身使用该模板；手持时由挂接到角色手部的表现实体使用同样部件描述。每段是独立动画部件，不要求每段都成为独立网络实体。资源量主要随部件数和布局数增长，不枚举完整组合。具体布局、资源规范与验收见《施法规则与运行时外观规格》。

角色的 swap_object 用作跟随锚点，不能连续覆盖同一符号来拼三段。对挂接表现实体内不同的 head、body、tail symbol 分别替换才构成完整法杖。必要时将表现拆为有限的前后层以适应角色遮挡；不能简单隐藏锚点后假设 follower 仍正常显示。P0 必须验证旋转、镜像、遮挡、握持、骑乘和卸下后的清理。

本地依据：balloon_held_child.lua 的 SpawnClientObject 将客户端表现实体通过 Follower 挂到角色 swap_object，并按网络字段替换部件；staff_lunarplant.lua 的 SetFxOwner 在角色手部和地面武器符号之间切换跟随；king_cane.lua 的 fx_OnGemFxDirty 根据同步的宝石类型替换独立宝石 symbol。这些证明接口路径存在，不等于三段法杖已经完成运行验证。预合成只保留为原型失败后的备选，不再作为默认量产路径。

库存图标不会自动继承地面 AnimState：使用自定义分层图标控件，以同一部件描述叠放 head/body/tail 图片。需要覆盖背包、容器、鼠标拖拽等物品图标入口，并验证兼容性；标准单图标接口提供通用备用图标，备用图标不能算作组合外观一致性验收通过。P0 需同时验证此项，避免只解决手持而遗漏库存。

客户端和服务端在公共构造阶段、SetPristine 与客户端返回之前声明一致的网络字段，之后服务端生成或加载实例数据。容量与紧凑外观描述为持久可复制状态；就绪状态、描述版本与数据一起校验，不能假设跨字段到达天然构成事务。客户端初始化后主动刷新并监听变化，在完整描述可用后统一应用；缺资源显示明确的兼容占位外观，不自行抽取另一套。

地面与手持通过各自模板的部件 symbol 设置，库存和预览通过分层 UI 设置；每处都从同一外观描述派生。晚加入、重新进入视野和转分片依赖当前复制状态恢复，而不是只在生成时发一次 RPC。切换装备时清理旧外观，属性尚未就绪时使用统一占位表现并禁止编辑。

法术格子使用自定义 Widget，客户端收到权威容量后生成对应数量的控件，服务端组件保存卡组。原版 container_replica 的槽数是本地字段，不能假设服务端 SetNumSlots 会自动改变客户端布局；首版不采用动态扩缩原版容器槽位的路径。编辑窗口打开时读取带修订号的完整快照，再开放操作。

## 施法语义与执行

以《施法规则与运行时外观规格》为规则依据，改用有状态抽牌解释器；取消固定前缀树合法性检查、缺蓝等待整组、尾部无效丢弃等旧规则。解释器维护牌库、手牌、弃牌堆和施法块；乱序只改变装填顺序，不另设简化语义。基础抽取与法术追加抽取分别标记，只有后者可以触发普通回绕。

在临时状态中逐卡检查和扣蓝，缺蓝卡进入弃牌堆并继续抽取；已成功执行的修饰不会因后续缺蓝而退费。预载完成后获得施法块及最终法力、牌区状态，经性能预算检查后原子提交并生成实体。原子提交保护联机一致性，不代表整组必须有足够法力才开始。预载成功但没有投射物也提交卡片消费及冷却，避免反复空转。

根施法块延迟与本轮回充修正分别累计；触发载荷在独立子块中预载，不直接把其施法延迟加给根块。本轮成功执行卡片的回充修正累加，包括回绕再次执行。两项修正后的时间最低均为 0 秒，最后等待取两者最大值；原版攻击动作、角色战斗冷却和法术专属冷却仍生效，专属冷却也计入触发载荷。

触发载荷保存施法者归属和完成预载的子块，命中或到时直接执行，不重新抽牌、不再次扣蓝。保持触发深度 2、执行节点 32 与有界抽取步数等安全限制；取消“首版不回绕”的限制。普通回绕与高级刷新环分开，首版不含刷新环及复制系列。资源预算失败的拒绝、回退与冷却规则见配套规格。

## 联机与物品编辑

客户端只能发送施法意图和编辑意图，不能提交伤害、法力结果或生成属性。服务端校验物品归属、装备槽、距离、存活状态、坐标有限性、目标合法性、冷却和请求频率。客户端瞄准坐标裁剪到有效射程；不得允许隔地图生成弹体。

高频状态采用小型网络变量同步法力显示、施法序号和状态位，避免每帧广播完整卡组。完整属性与卡组在检查物品或打开编辑器时发送受限快照；大型数据使用有版本号、有大小上限的消息，而不是假设任意网络字符串都足够长。HUD 可插值，但真实扣蓝只能由服务端决定。

编辑采用“物品实例标识 + 当前修订号 + 新槽位方案”事务。服务端确认玩家靠近工作台、持有对应卡片、没有并发编辑或施法，再原子转移物品并增加修订号。失败不消耗卡。断线、关闭面板、丢弃法杖和离开工作台都取消编辑会话；不得复制卡片。拖动只改变本地草稿。

法杖作为物品携带所有持久状态通过分片迁移；每个分片独立运行施法与弹体预算。活动弹体不跨洞穴入口迁移。需验证库存、背包、容器、死亡掉落、交给队友及地面转洞穴后的完整性。

## 弹道与伤害

伤害、碰撞和目标选择在服务器执行；客户端只运行视觉插值。直线弹首先验证现成 projectile 是否适合自由瞄准；目标追踪型接口不足时使用独立运动与碰撞逻辑。

高速弹使用上一位置到当前位置的线段扫掠和候选目标距离检测，避免仅按帧末位置判断而穿过小目标。范围查询设置半径、数量与标签限制；追踪降低扫描频率，弹跳限制次数，穿透记录已命中目标。伤害走目标 combat 等组件接口以保留护甲、仇恨与击杀归属；控制效果检查对应组件、标签和抗性。

首版保护规则统一应用到直接命中、爆炸、电弧、持续伤害和吸血，禁止每种法术各自遗漏检查。照明光源和残留特效有明确寿命。火焰默认采用视觉及自定义灼烧伤害，不直接点燃附近可燃物。

建议初始预算：每玩家最多 24 个活动伤害弹体、单次最多 12 个新弹体、每分片最多 160 个；弹体寿命最多 5 秒。预算只是待测起点，达到上限时反馈“奥术过载”并限制新施法，不能静默删除其他玩家弹体。表现粒子单独限额，不能用关闭粒子代替限制服务器伤害实体。

## 存档与升级

OnSave/OnLoad 保存剩余时长而不是机器绝对时间；加载时夹取数值边界、校验卡片 id 与版本。未知卡保留为可取出的失效卡，避免整个物品无法加载。存档升级按 schema_version 逐步迁移，加载旧存档不重抽法杖。

法力在物品休眠时可按世界时间差惰性恢复，在使用、检查与保存时结算，避免每把箱内法杖都有常驻任务。离线不累计现实时间收益。回滚恢复同一快照，不承诺抵御游戏自身世界回滚导致的重新掉落。

卸载 Mod 前应提示移除自定义物品并备份世界；不能承诺移除 Mod 后其物品继续存在。开发测试使用独立世界与存档备份。

## 美术与输入

准备原创杖头、杖身、杖尾及储能装饰资源，通过短／中／长动画布局运行时组合地面和手持表现，库存与预览使用分层控件；另准备 24 个法术图标、弹体与命中特效，以及编辑面板。初始素材数量与属性映射见玩法方案。先以合法占位资源验证逻辑，再导入最终资源并验证打包。所有客户端需要相同资源。Noita 美术与音效不直接移植。

验证键鼠自由瞄准、移动取消、连续施法、聊天输入屏蔽、界面缩放与不同分辨率；编辑器显示耗蓝、延迟、回充、作用范围和无效组合原因。后续手柄支持单独安排导航与地面选点，不声称复用鼠标拖动即可支持。

暂不承诺工期；P0 的弹道和 UI 验证后再估算。性能原型失败时先降低弹体数或改进模拟，再评估是否调整复杂轨迹，不能在未说明情况下删减首版目标。

测试矩阵覆盖：玩家建房、无界面专服、地面与洞穴；1／2／4／6 人；正常网络与模拟 100／200 ms 延迟；保存退出、重连、死亡、传送、丢弃、交易、容器、编辑中断。记录实际测试硬件和网络条件。

纯 Lua 自动测试覆盖抽牌解释器、费用、修饰作用域、乱序与回绕、预算边界与存档迁移；10,000 个生成样本检查非法属性和极端分布。游戏集成测试覆盖护甲、抗性、Boss、友军保护及触发器只执行一次。持续 30 分钟压力测试检查弹体清理、实体数量回落和日志异常。

外观验收覆盖乱序与非乱序、1／2／3 发、容量 4→5 与 8→9 的长度分界，以及法力和回复档位边界；检查部件接缝、方向、遮挡、连接点和不同角色握持。验证库存小图、地面、手持、检查预览表达一致；装备切换、死亡掉落、骑乘、重连、晚加入和存档恢复后不换样、不串图。生成样本自动检查所有外观 ID 存在，且视觉标记与基础属性一致。

性能目标暂设为六人连续施法时服务器帧耗时 p95 相对空载增加不超过 5 ms；必须附硬件、世界负载和测量方式，实测后才能认定达标。兼容检查至少包括常见背包／容器改动与 HUD 类 Mod；未测试的 Mod 不宣称兼容。

## 下一轮开发前的设计取舍

当前建议默认采用：PvE 无友伤、无营地纵火、法杖不掉耐久、仅工作台编辑、卡片可拆卸交易、首版 12 格上限与有界触发。用户可据此调整偏生存平衡或偏 Noita 高强度弹幕；两者会影响数值、性能预算和获取路线，但不改变服务端权威架构。

本轮交付到此为止。后续实施以用户确认后的玩法范围为准。
